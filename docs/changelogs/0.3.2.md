# Changelog: Celeris v0.3.2 (1.21 – 26.3)

The native parts work again: in 0.3.1.1 they were built with function names Java could not link, so native zstd and the native physics kernel never loaded and Celeris quietly used FFM or plain Java. This release fixes that, guards every future release against it, and brings a set of fixes and a faster shared worker pool. Nothing that worked before is taken away.

---

## Key Features & Changes

* **Native Code Loads Again**: The physics kernel and the zstd shim export the names Java expects (`Java_net_bichal_*`), so native zstd runs out of the box again and the native physics kernel can be used without launch flags. A build check now compares every `native` method with the symbols the libraries export, and the release gate refuses a release when they differ.
* **Native Physics Is Opt-In**: Without a request, physics runs on the pure-Java kernel. Measured side by side, the native kernel steps items about twice as fast, but that step is only a few percent of a server tick, and on a real server the engines tie. A mod that has room for it asks with `CelerisPhysics.allowNative("modid")` before its first batch (Velox does). `-Dceleris.physics.engine` still has the last word: `java`, `auto` (native for every mod), `jni`, `ffm` or `off`.
* **Shared Worker Pool**: Up to four threads can now hand work to Celeris's worker threads at the same time. Before, a second caller was turned away and did all of its work alone on one core, which is what happened to a mod's load-time work whenever another thread held the pool.
* **zstd Only When Used**: The compression codec is chosen the first time a mod compresses something, instead of at startup. If no mod compresses anything, libzstd is never loaded. The log says `Celeris compression codec: chosen on first use` at startup and names the codec when it is first used.
* **Faster Native Kernel**: The per-item input check costs less (one bit-pattern test on x86, FACGE on ARM), and a clamp it already covers is skipped. Results are bit-identical; the step is 3 to 10 % faster in batches of 1,024 on x86.
* **Network Fixes**: Received payloads are no longer decompressed on the network thread only to be thrown away; just their header is checked. Sending a payload above the 1 MiB wire limit now fails where it is sent.
* **Sturdier Internals**: The dirty-mark queue no longer loses or duplicates marks while it grows, keeps updates when its ring is full, and frees its memory when closed. The heap memory backend rejects stale handles. The message ring cannot get stuck after a failed publish. The JNI kernel checks every entry point when it loads, so a library missing one falls back instead of failing at the first tick. Entity and pipe-network edge cases (an entity removed mid-tick, NaN speeds, a listener that throws) are handled.
* **For Mod Authors**: New `PayloadCompression.validate`, `TransitDeltaRecorder.droppedOperations`, `LongRingDirtyQueue.close`, `CelerisPhysics.allowNative` and `ChunkWorkers.MAX_CONCURRENT_RUNS`. The unused `compression_algo` setting is gone. Building Celeris from source needs JDK 25 for Gradle.
